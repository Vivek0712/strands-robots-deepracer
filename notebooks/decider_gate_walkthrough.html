A Strands Decider 2B gate on a robot's motor commands¶

This notebook walks through the one decision I hand to Strands Decider 2B in the strands-robots-deepracer project: before the agent's motion tool runs, is the move inside the envelope the operator briefed, is it grounded in what the user actually said, and what is in front of the camera right now. The decider answers typed questions with calibrated probabilities; a few lines of plain Python turn those probabilities into one of the four Strands intervention actions (Proceed, Guide, Confirm, Deny). You need no car and no GPU to run it.

The declared hackathon pattern is Guardrails (#strands-decider-2b, #guardrails): before a tool call, verify the arguments are grounded in what the user actually said. The repository is https://github.com/Vivek0712/strands-robots-deepracer. The typed questions are inside_envelope (yes/no), args_grounded (yes/no) and intent (five-way choice) over the words, and person (yes/no) and frame (five-way choice) over the camera frame.

What you will learn:

  1. The System One API: one POST /v1/systemone with a noul, a choice and a score question.
  2. The typed question set the gate sends before every move, as JSON.
  3. How a grounded command and an invented one map to different intervention actions.
  4. How the same request shape judges a camera frame (person, obstacle, clear, unclear), and what the gate does when the decider fails, answers late, or is not there.
  5. What the gate costs: measured latency on this machine next to the recorded booth-model numbers, and the local 2B next to Amazon Nova Pro on Bedrock answering the same grounding question.
  6. How the gate plugs into a Strands Agent on Amazon Bedrock, with a run recorded against the real model.
  7. How to take the pattern into your own agent in three steps.

The safety line, which I repeat everywhere this project is described: physics stops the car (the pen lip, the hop cap, the on-car deadman, the marshal's thumb on the battery switch); the decider explains. Nothing in this notebook is a safety layer. It is the layer that gives every stop a reason a person can read.

1. The System One API in one request¶

A Strands Decider is a decoder torso with its language-modelling head replaced by a small pointer head. It does not generate text. It reads a state once and answers every question in the request in one forward pass, so three questions cost about the same as one. The HTTP contract is POST /v1/systemone with {"state": ..., "model": ..., "questions": {name: {"type", "instructions", "criteria"}}}, and that is all the client below is. The model field names the checkpoint the request was written for; the library sends it on every call, so the hand-written request here does too.

The three question types:

  • noul, a yes/no, comes back as P(true).
  • choice, one of N named options, comes back as the chosen option plus a probability per option.
  • score, an ordered rubric, comes back as the expected level on that rubric.

I send one text state in the DeepRacer gate's own vocabulary (the car's tool is drive_deepracer(linear, angular, duration)): the operator's words, the drive the agent proposes and the briefed envelope, with one question of each type.

Reading the answer:

  • inside_envelope.noul is P(true) and that is all a noul carries. The server reports no separate confidence for a yes/no; how far the number sits from 0.5 is the whole story, which is why the gate uses one threshold YES and its mirror 1 - YES.
  • intent.probabilities has one entry per option and sums to one. intent.choice is the argmax. intent.confidence is a separate number defined for a choice, (N * p_max - 1) / (N - 1): it is 0 when the options are equally likely and 1 when one option takes everything. A choice can be the argmax at p = 0.4 and still have low confidence, so the gate thresholds on the chosen option's own probability, never on choice alone.
  • margin.score is the expected level on the rubric (0 is the first level), legend maps level numbers back to the words, and probabilities is the distribution over levels. Its confidence is 1 - sigma / sigma_max: 1 when the mass sits on one level, 0 when it is spread as wide as the rubric allows.
  • latency_ms is the server's own measurement; the gate records the client round trip instead, because that is what a stop budget cares about.

On the fake decider the noul comes from the numbers in the text (0.95 inside, 0.05 outside, 0.5 when nothing parses), a choice that is not about the camera takes the first option at 0.6, and a score lands on the middle level. On the booth model these are the model's own judgements; the recorded ones are in section 5.

2. The typed question set the gate sends before every move¶

The reusable pattern lives in patterns/strands/, with the file names of the upstream strands-decider quickstart so recipes written against either are interchangeable: _client.py (the stdlib Decider with Decider.noul, Decider.choice, Decider.score, .ask(state, questions, images=None), and ServerUnavailable for a server that does not answer), tool_call_intervention.py (the QUESTIONS dict, the YES threshold, the MotionGate intervention handler and a small Envelope) and frame_intervention.py (the vision variant: FRAME_QUESTIONS, FRAME_CLASSES, FrameGate).

The questions are data. Nothing is baked into the model: option names and the true/false descriptions are read from the request, so changing the policy is editing a dict. Every Decider below gets the gate's budget, timeout=1.5, the same number the recipes and the car use: past it the gate denies.

3. Grounded versus invented¶

The hackathon pattern I declare is Guardrails: before a tool call, verify the arguments are grounded in what the user actually said. Two conversations make the point. In the first the user says "roll forward twenty centimetres" and the agent proposes move(distance_m=0.2). In the second the user says "a little forward" and the agent proposes move(distance_m=2.0): a number nobody said, four times the envelope. I drive MotionGate.before_tool_call directly with a stand-in event, offline, no Bedrock call, exactly as Strands would call it inside an agent. The handler is async; in a script the library's judge(gate, event) runs it to completion, and a notebook kernel already has an event loop, so here I await it.

MotionGate builds one state (the conversation, the proposed call, the envelope and the result of its own arithmetic check), asks the three questions, and then its decide method maps the numbers. Rows are checked in this order and the first matching row is the action (the numbers are the rows of the shared thirteen-row table in the project README; the frame rows of section 4 sit between 1 and 6):

# Condition Action Reason
1 decider unreachable, timeout (> 1.5 s), malformed answer Deny decider unavailable
6 intent stop with p >= 0.65 Deny the user asked to stop
7 arithmetic envelope check fails (code, not the model) Guide (on the car: Confirm, the marshal may approve a bigger hop) outside envelope: ...
8 inside_envelope < 0.35 Guide: re-plan inside the envelope outside envelope per decider
9 args_grounded < 0.35 Guide: ask the user for the values arguments not grounded
10 intent question or unrelated with p >= 0.65 Guide: answer the user instead intent ...
12 inside_envelope or args_grounded in [0.35, 0.65) Confirm: ask the operator unclear
13 otherwise Proceed inside envelope p=..., grounded p=...

Thresholds and mapping are owned by the code, not the model.

What the fake decider did here, and what the booth model does: the fake has no language model. It reads the gate's deterministic_check line and answers both yes/no questions from it (0.95 when the check passed, 0.05 when it failed), so on the fake the invented case is caught by the arithmetic in code and the decider agrees. The booth model reads "a little forward" against the 2.0 and answers the grounding question on its own: on 2026-10-22 it read args_grounded at 0.78 or above for every grounded case and at 0.63 or below for every invented one (section 5), and the recorded envelope answers (mean P(inside) 0.92 for a 0.2 m/s hop, 0.10 for 0.5 m/s, from docs/results/decider-benchmark-2026-10-14/q2610.json) show what a calibrated yes/no looks like on this model.

4. Seeing: the same request shape on a camera frame¶

The second request before every move carries the latest camera frame as a base64 JPEG in images and two questions over it: a yes/no "is a person visible in the frame?" and a five-way choice over clear, obstacle_near, person_in_frame, off_surface, unclear. Rows 1 and 2: a missing judge is a stop, never permission¶

The fake decider has two knobs for proving this: /control?fail=1 makes every answer an HTTP 500 and /control?latency_ms=3000 makes every answer take three seconds, twice the gate's budget. Both gates get a Decider(timeout=1.5) and their own timeout=1.5, so the socket and the handler give up together. After that: no frame at all, and a Decider pointed at a port where nothing listens, where the client raises ServerUnavailable and both gates turn it into a Deny. The same thing happens on a malformed answer (a missing key, a probability outside [0, 1] or NaN, an unknown class): the gates check every number before they compare it, so a garbled body cannot fall through to Proceed.

6. Wiring it into a Strands Agent on Amazon Bedrock¶

In the project the language model on Amazon Bedrock proposes the move and the local decider judges it. The wiring is one line: interventions=[MotionGate(Decider(timeout=1.5))]. Strands calls before_tool_call before the tool runs and acts on the returned Proceed, Guide, Confirm or Deny; Guide hands the model its turn back with the feedback text, so an agent that invented a distance ends up re-planning or asking the user instead of driving, and Confirm stops the run with an interrupt for the operator to answer. The cell answers that interrupt the way the library's main() does: it prints the question, answers "no" and resumes the agent with the interruptResponse shape Strands expects.

The move tool, the eager system prompt (it tells the model to assume two metres when no distance is given, which is the failure the gate is there to catch), the two requests and the default Bedrock model (us.amazon.nova-pro-v1:0, BEDROCK_MODEL_ID overrides) come from the library. The tool touches no motor: it returns what it would have done. On the DeepRacer the same seam sits in front of drive_deepracer, and upstream strands-robots puts its own operator command gate behind that.

Two wiring details the recorded run below taught me. The agent gets a SequentialToolExecutor, because a model may propose several moves in one turn and Strands would otherwise run them, and the gate's requests, concurrently; the 2B on Metal takes one request at a time. And the cell sends one warm-up ask before the agent starts, as the production gate's warm_gate does, so the first hop is not the cold one.

The cell is guarded by RUN_BEDROCK so the saved notebook shows the code and a note rather than a failed call on a machine without AWS credentials.

7. Take it with you¶

Three steps put the same gate in front of any Strands tool:

  1. Serve a decider and copy the library. strands-decider serve StrandsAgents/strands-decider-2B-qwen3.5-v1-2610 --vision --port 8111, then copy patterns/strands/_client.py and patterns/strands/tool_call_intervention.py next to your agent. Both are stdlib plus strands-agents; nothing else to install.
  2. Write your questions. Edit QUESTIONS: the true/false descriptions and the option names carry most of the signal, and they are read from the request, so there is nothing to retrain. Put the deterministic facts you already know (limits, a validator's result) in the state next to the question; section 5 shows what that buys.
  3. Register the handler. Agent(model=BedrockModel(...), tools=[...], interventions=[MotionGate(Decider(timeout=1.5))]). Map probabilities to Proceed, Guide, Confirm or Deny in code you own, and give the Decider the same budget as the gate so a hung server is a Deny in 1.5 s, not a two-minute wait. If your server takes one request at a time, as the 2B on Metal does, add tool_executor=SequentialToolExecutor().

The tuning knob is YES in tool_call_intervention.py: a noul at or above it is a confident yes, below 1 - YES a confident no, and the band between (including 1 - YES itself) is a Confirm. Lower it to confirm less, raise it to confirm more, and set it from measured probabilities on your own traffic, the way docs/results/decider-text-questions-2026-10-22.md does for the grounding question and docs/results/decider-calibration-2026-10-14.md does for the frame question, never by feel.
